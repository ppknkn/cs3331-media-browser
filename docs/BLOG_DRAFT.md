# 用 Agent Team 完成软件工程作业：一个本地 Web 媒体浏览器的开发记录

这次 CS3331 软件工程作业，我尝试让一个主控 Agent 调度三个角色，完成一个可以运行、可以测试、可以交付的项目。题目是本地 Web 媒体浏览器：打开电脑上的文件夹，把子文件夹作为图集，浏览图片、播放视频，并提供现代化的界面。

我给团队规定了顺序：CodeWriter 先实现完整程序，CodeReviewer 独立评审，评审没有严重问题后，由 TestEngineer 阅读源码、编写测试并在终端执行。问题交回 CodeWriter 修复，再复评或回归。主控负责需求、交接、独立验收和最终提交。

## 先确定「打开本地文件夹」的含义

这个需求看起来简单，却决定了前后端的边界。网页直接得到一个目录句柄，与本机后端拿到一个可读取的路径，是两种不同的接口。浏览器原生的目录选择 API 还有兼容性和使用条件。

因此项目采用本机服务：Python 后端读取用户选定的目录，浏览器负责呈现。网页可以调用系统文件夹选择窗口，也可以手动输入绝对路径。媒体通过本机地址读取，不上传云端；程序不修改用户的照片和视频。

当前 workspace 已经有一个课程管理程序。这次开发把新项目放在独立的 `media-browser/` 子目录，避免覆盖已有程序，也避免将已有个人课表和数据库一起推到公开仓库。这个决定发生在开发开始前，而不是到提交时才补救。

## 三个角色如何交接

| 角色 | 输入 | 输出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| CodeWriter | 需求、环境、接口与边界要求 | 完整程序、入口、运行文档、实现说明 | 程序可交给另一个角色检查 |
| CodeReviewer | 实际源码与需求清单 | 分级问题、位置、复现条件、建议 | 严重问题已经修复并复评 |
| TestEngineer | 评审后的源码 | 测试代码、终端输出、报告 | 用例通过，发现的问题完成回归 |
| 主控 | 各角色交付与验证证据 | 浏览器验收、迭代记录、最终报告与 GitHub 提交 | 交付项完整且远端提交可核验 |

这里有一个重要约束：角色名称不会自动带来独立性。评审者需要自己读代码，测试者需要独立编写并执行用例，主控还要检查页面实际能否使用。把开发者的一句「完成」复制到报告里，不能代替这些步骤。

## 为什么选择标准库后端与原生前端

环境检查确认指定的 conda 解释器是 Python 3.10，已经有 pytest 与 Pillow，但没有 Flask。应用采用 Python 标准库 HTTP 服务，加 HTML、CSS 和 JavaScript。运行项目不需要安装前端构建工具或第三方 Web 框架。

这个选择降低了交付门槛，也把协议处理责任交给了项目本身。视频分段请求、路径验证、请求体限制、错误响应都必须明确实现并验证。测试工具则单独列出，不把本机已经安装的工具误写成应用的必要依赖。

## 图片网格背后还有哪些问题

图库页面很容易让人先关注卡片、颜色和动画。但完整链路还包括目录导航、特殊文件名、空文件夹、读取权限、加载失败、切换文件夹时未完成的请求，以及视频播放后的关闭和资源释放。

后端为打开的文件夹维护切换标识，目录请求与媒体 URL 都带上这个标识。用户切换目录后，旧请求可以被识别并拒绝。路径访问则基于选定根目录校验，不能仅凭字符串前缀判断：目录穿越和符号链接都可能让一个看似位于图库里的路径指向外面。

视频部分也需要完整的前后端配合。浏览器播放器拖动进度时可能请求一段字节。后端需要处理有效范围、开放范围、后缀范围和越界情况，并给出一致的响应头与正文。将完整视频读进内存再返回，会让小样例掩盖大文件使用时的问题。

## 怎样记录问题与验证

项目使用三类证据：源码评审、终端测试、浏览器实际运行。它们回答不同问题：源码评审检查逻辑和边界；测试确认特定输入下的响应；浏览器验收检查用户是否真的能完成导航、查看、播放和拖动。

每个问题记录发现者、触发条件、影响、修复方式和复验结果。失败的测试输出也应保留，让开发记录呈现真实迭代，而不只有最后一次成功的数字。

## 独立评审实际找到了什么

首轮评审没有发现 P0/P1 严重阻断问题，但登记了 4 个 P2 和 1 个 P3。这里不是为了凑一份风险清单：评审者使用人工目录和小文件复现了其中四项，另一项明确注明来自源码事件链推演，留给浏览器测试确认。

| 问题 | 实际现象 | 修复方向 |
| --- | --- | --- |
| 扫描预算共享 | 小预算下第一个图集耗尽预算，后续同级图集和根媒体消失 | 当前层发现与子图集统计使用独立预算 |
| 加载状态未清理 | 新图集尚未返回时，工具栏可以将旧图集重新画出来 | 开始请求时废弃旧数据，并验证请求代次 |
| Windows 联接识别 | 指定 Python 3.10 没有 `Path.is_junction`，库内目录联接重复成图集 | 使用兼容当前解释器的重解析点属性检查 |
| HTTP Range 语义 | HEAD 带 Range 返回 206，未知范围单位返回 416 | HEAD 忽略 Range；未知单位和未实现的多段范围返回完整内容 |
| 异常令牌 | 非 ASCII 请求头触发字符串比较异常，错误变成 500 | 无效凭据统一返回 403 |

Windows 的问题特别有代表性。代码中有一个看似合理的兼容性判断：存在较新的方法才调用它。可是当方法不存在时，实际需要的联接排除逻辑也一起失效了。评审者在指定的 Python 3.10 环境创建真实 NTFS 联接，才把这个问题和文档承诺对照出来。这里的后果是重复入口，报告没有将它夸大为已经证实的越界读取。

第一次修复后，评审者又发现扫描上限仍未真正落地。代码把顶层发现和递归预算分开，却还通过 `sorted(iterator)` 一次读完目录再处理预算，顶层也没有独立上限。这说明“修掉最先出现的症状”还不够：需要同时保持同级导航入口、限制实际枚举工作量，并给出部分统计提示。主控因此再次将问题交回 CodeWriter，测试者增加对枚举消费次数的回归检查。

评审日志还有两项被排除的疑虑：`pythonw` 的子进程输出经小验证能够捕获；本机网络与路径读取权限错误来自执行环境限制。这些现象没有混进程序 bug 数量里。

## 测试工程师也需要检验自己的测试

后端第一次在受限环境执行时，被临时目录读取权限阻断。换到获准的本机执行环境后，首轮正式结果为 52 项通过、0 项失败或错误、1 项跳过。跳过的原因是系统没有创建符号链接的权限；真实 Windows 目录联接的越界与循环用例已经执行。测试者继续补充可执行的符号链接分支替身，并保留真实符号链接未实测的说明。

浏览器首轮通过了前 10 项，包括 H.264 视频实际播放时间前进、跳转到 2.5 秒、图片切换与缩放、Escape 后焦点恢复。但延迟请求测试随后出现了 Playwright 的 `Route is already handled`：测试脚本在路由处理尚未完成时注销了它。TestEngineer 修复的是测试脚本，等待路由继续处理完成再注销，然后重新运行完整浏览器验收。这个失败不能算作应用缺陷，也不能从开发记录里删掉。

这样的记录比一个没有上下文的通过率更有用。执行权限问题、测试框架问题和产品问题需要分别定位；否则团队可能在错误的文件上反复修改。最终数字和原始日志均保留在项目测试报告中。

主控在上传前又核对了一次机器可读证据，发现整轮浏览器运行只有几秒，单个用例的 `seconds` 字段却出现 473。原因是脚本使用 `performance.now()` 的毫秒差值，却给字段命名为秒。主控将问题交回 TestEngineer，除以 1000 后重新跑验收。旧 JSON 不被暗改，报告明确指出它的旧耗时字段实际是毫秒。通过数没有变化，但证据的单位需要正确。

这个小问题提醒我：主控的工作不能停留在转发「16 项通过」。最终检查还应包括记录是否自洽、环境是否明确、失败是否保留，以及报告对应的源码是否一致。

## 公开提交也有一次真实迭代

用户选择的是公开 GitHub 仓库。第一次推送在执行前被自动审批拦下，因为测试日志包含本机用户名和绝对路径。仓库当时仍为空，没有已经发布的泄漏需要撤回。团队把未脱敏证据单独留在本机，公开副本用路径占位符替换私人目录，测试数字和错误过程保持不变；提交身份使用 GitHub noreply 邮箱。首次提交尚未发布，因此可以重建该提交，避免仅追加一个清理提交却把旧内容继续留在历史中。

截图只使用人工媒体，也可能带出完整本机目录。TestEngineer 第一次尝试通过临时样式隐藏路径，但应用的 CSP 拒绝了样式注入，最终控制台断言失败。团队没有削弱应用限制或放过报错，而是使用元素原生的 `hidden` 属性，拍摄后恢复，再跑完整 16 项验收。这次 16/16 通过，公开截图也逐张复核。这个问题属于交付和测试工具，不属于媒体播放功能。

这里形成了一个具体经验：公开的是经过审核的证据副本，原件仍应留存；脱敏应说明修改范围，不能悄悄修改失败结果或计时数据。

## 可复用的经验

1. 在开工前明确文件和目录的边界。既要保护用户选中的媒体目录，也要保护 workspace 中已经存在的项目。
2. 给每个角色具体的输入和交付物。把「评审一下」细化为问题位置、严重程度和复现条件，把「测一下」细化为可重复执行的用例与终端输出。
3. 测试要覆盖前后端之间的契约。文件夹切换标识、媒体 URL、Range 响应和界面状态，比孤立检查某个函数更能暴露实际故障。
4. 将通过的范围写清楚。自动化替身验证原生选择器的接口分支，不等于真人已经点击系统对话框；一个浏览器播放了一种 MP4，也不代表所有视频编码都兼容。
5. 交付包含复现条件。源码、测试、原始输出和运行命令一起保留，博客里的结论才能被读者核对。
6. 修复要回到最初的验收条件。扫描可以看见其他图集，不等于扫描已经有界；复评者需要检查修复后的整体行为，而不只看一条补丁。
7. 公开交付要检查文档、日志、截图和 Git 历史。人工测试素材不能自动保证截图不含本机路径，清理工作树也不能自动清理先前的提交。

## 最终交付与已验证的范围

本机最终后端共有 54 项测试，53 项通过、1 项因创建真实符号链接的系统权限限制跳过，0 项失败、0 项错误。16 项浏览器验收通过，覆盖实际媒体播放与进度跳转，以及延迟加载、部分统计和错误恢复。跳过项没有计入通过数，Windows 目录联接与符号链接分支替身的验证分别记录。

远端结果补充了本机限制：两组 Windows 后端均 54/54 通过，两组 Ubuntu 均 53 通过、1 个 Windows 专属目录联接测试跳过；四组真实符号链接越界和循环均成功。TestEngineer 阅读实际日志后才把这项写入结论。本机跳过仍保留原记录，远端验证作为另外一层证据。

源码、独立测试、评审报告、经路径脱敏的成功与失败输出、四张截图和团队开发日志一同交付。仓库为 [cs3331-media-browser](https://github.com/ppknkn/cs3331-media-browser)，以 CS3331 软件工程作业标注。2026-10-10 的 [GitHub Actions 实际运行](https://github.com/ppknkn/cs3331-media-browser/actions/runs/38052873416) 已完成，Ubuntu/Windows 与 Python 3.10/3.12 四组后端测试和 JavaScript 语法检查全部成功；完整网页交互和视频验收在本机 Edge 完成，两种验证范围分别记录。

上传还有一个环境问题：现有 HTTPS 登录没有提交工作流需要的权限。主控验证本机已经配置的 SSH 身份属于同一 GitHub 账户，使用该身份完成推送。这里无需让用户重新登录，也没有为绕过问题删除自动测试配置。

这次没有把替身测试写成真人操作系统对话框，也没有把一种 H.264 视频播放成功写成所有视频编码都兼容。截图均为人工生成的演示素材，公开仓库没有用户媒体或原有课程程序的个人数据。详细复现步骤与范围可查阅仓库中的 [测试报告](https://github.com/ppknkn/cs3331-media-browser/blob/main/docs/TEST_REPORT.md)和[开发日志](https://github.com/ppknkn/cs3331-media-browser/blob/main/docs/DEVELOPMENT_LOG.md)。
